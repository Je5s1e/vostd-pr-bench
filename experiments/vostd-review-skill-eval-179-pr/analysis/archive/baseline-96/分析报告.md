# VOSTD review 运行效果分析（2026-11-21 固定截点）

目前这次 **fast static review 能较稳定地发现显式证明信任缺口，但对规范细节、资源关系以及构建/工具链问题覆盖不足**。更重要的是，这批结果不能直接视为完整 `vostd-code-review` skill 的能力测评：96 份报告都声明采用 fast 模式；标签又混有快照存量问题和已被 PR 修复的问题。需要同时改进运行方式、检测方法与评测任务定义。

本次仅在 `analysis/review-eval-20261121/` 新增分析文件，没有修改 `vostd-pr-test`、`vostd-pr-bench`、skill 或运行中的 review。没有重跑历史 Verus、构建、测试，也没有启动新的 PR review。

## 1. 样本与评测口径

- 固定截点：`2026-11-21T06:20:57.921502Z`（纽约时间 2026-11-21 01:20:57；采集机器返回的等价时刻为 `14:20:57+08:00`）。
- 当时有 **96/179 个快照样本**生成了非空、带结论及 Evidence check record 的 review（53.6%）。以文件产物判断完成，不声称已读取任务调度器的完成状态。
- 96 个样本对应 **85 个不同 PR**、**117 个标签**。多个 SHA 的同一 PR 分别评测，不能将“样本数”说成不同 PR 数。
- 全基准有 244 个标签；当前截点覆盖其中 117 个（48.0%）。所有已评样本都至少有一个标签，没有可用的无缺陷负样本。
- 精确按 `pr-编号-SHA前缀` 配对；96/96 的 `diff.patch` 与基准逐字节一致。标签引用的 126 个不同“样本/版本/文件”也全部逐字节一致，排除了这些输入文件错配。
- 截至最终复查（06:28:20Z），分析期间新增 `pr-646-5053290d119e`、`pr-65-625495f69559`、`pr-651-4fe5602573ae`、`pr-656-ffafeb7a696a` 四份报告，**不计入本次冻结分母**。原有96份报告复查时哈希均未改变。这不是运行结束后的最终评分。

采用人工、逐根因语义匹配，不用关键词相似度代替裁决：报告需要指出相同对象的失败机制或欠缺的具体证明义务。仅同文件、同规则、同属“有 assume”不算命中。一个报告 finding 可以覆盖两个明确指出的标签；一个标签也可能由两个 finding 合并覆盖。对同根因的多个位置不要求逐个重复，但不能仅泛称“还有证明债务”。

- **F 完整命中**：准确指出标签根因与影响，证据/修复指向同一问题。
- **P 部分命中**：仅覆盖一个相关子义务，或命中问题族但定位到旧约束，具体说明见逐条表。
- **M 未匹配**：报告没有指出标签根因，不自动断言 skill 本应在该 diff 范围检出。
- **X 已修复/任务不相容**：标签定位 before 的问题，但 after 已修复；原始对齐分母保留，另给剔除后的敏感性结果。

这是单一评估者的判断，不是独立多评审共识，也不是新一轮源码真值认证。基准标签是本次参照真值；大多数历史标签本身也使用 source-only 裁决。完整标签、理由、原始报告和指纹保存在 `snapshot.json`，逐标签判断见 `逐条匹配.md` / `label_matches.csv`。

### 报告产出量与未匹配意见

96份报告共抽取 **174 条 finding**：High 87、Medium 74、Low 13。High/Medium占92.5%，报告整体偏向阻塞和合并前问题。

- 43条 finding 完整匹配至少一个标签；3条仅部分匹配；128条未匹配。
- 因存在多对多关系，43条完整匹配 finding 与42个完整命中标签并不矛盾。
- 43/174=24.7%是**已标注根因的对齐比例，不是 precision**。
- 128/174=73.6%是未标注/未匹配比例，**不能说成73.6%误报率**。其中可能有真实的新问题、范围外旧问题、与标签不同的建议，也可能有误判。
- 没有逐条独立裁决这128条的真伪，也没有无缺陷负样本，因此不报告 accuracy、FPR、specificity 或正式 F1。用117个不穷尽标签硬算 precision 会误导。

## 3. 哪些检测做得好

**显式证明缺口及其调用者影响相对可靠。** #226的view invariant、empty constructor、push三个标签全部命中；#237的align-up/down两条链路均命中；#183的alignment theorem与carry-preservation也全部命中。报告不只是搜索 `admit`，通常能说明该可信事实如何进入公共后置条件。

**局部明确的契约矛盾也能识别。** #119准确指出old/post-state PTE地址混用；#382 `045f…` 同时抓到None/retry/unwrap、可信Some契约不实及callee丢失caller所需保证。#617正确指出getter的ghost快照未绑定receiver，这是资源身份组中的正例。

**显眼的运行时退化有一定覆盖。** #337的preemption guardian失效、#456的DMA平台设置缺失、#501的activate panic、#505的heap API被注释、#515的const constructor移除均有对应命中。但这不能推广为对所有生命周期问题都强。

## 4. 主要弱点与可复核案例

### 4.1 以新信任原语为线索，容易忽略没有新增 assume 的语义问题

#632报告强调“axiom改proof、没有新增assumption”，却未识别ghost账本能在不消费tracked obligation的情况下清空。#64关注allocator的trusted contract，却漏掉 `len == 512` 与 `len < 512 ==> ...` 使PTE不变量真空化。#213 `7de4…` 报告 admitted liveness，但漏掉 existential 选域外线程使lock-freedom vacuous。

改进应从“有没有信任原语”推进到“这个命题是否可能空真、资源是否真正守恒”。原语数量减少不是模型正确性的证据。

### 4.2 跨对象、跨分支和生命周期推理不足

#143漏掉child guard与parent缺same-instance/PTE联系；#419漏掉ghost sequence转tracked sequence的资源复制；#439漏掉Err路径消耗owner；#547漏掉可变借用结束状态与公开mutable node的冲突。运行时方面，#122漏掉guard未释放底层spinlock，#395漏掉downgrade缺wake，#104漏掉页表边界处未升层/未清slot。

这些问题不能靠仅检查签名或当前成功caller发现。应逐条跟踪输入权限、输出权限、Err/None分支、drop、unlock、wake，以及对象身份关系。

### 4.3 fast 模式遗漏低成本的结构规范检查

原始guideline召回仅4/26。按guideline标签自身rule_id细看：`name-proof-roles`为2/6；`reuse-existing-specifications`为0/4；`avoid-redundant-mode-markers`为0/2；导入分组、无用导入、冗余cast、局部lint各有漏检。

#614明确review了tracked constructors但漏掉对应命名；#636把新构造前置条件视为合理，却未检查 `has_safe_slot` 已覆盖的重复约束及链式比较；#452给了“向upstream提议标准库spec”的意见，却未抓到标签要求复用已有 `is_pow2_exists`。这说明大方向检查并不能替代逐条规则覆盖。

文档方面还存在任务政策冲突：skill明确排除 completeness-only 文档意见；#382的参数/义务文档完整性标签可能受到该政策抑制。#577描述已不存在字段则是失实文档，应与完整性nit区别处理。

### 4.4 构建/工具链问题缺少专门的第一道检查

#100不存在的 `pa` 字段、#33缺模块文件、#226错误trait receiver、#526缺required trait methods均漏检。#16/#17的termination policy和#22/#235的证明可接受性问题也没有命中。#220缺 `fi` 未被识别，报告反而先讨论执行后的pipeline状态。

不能把这些漏检全部归因于不运行Verus：缺字段、缺模块、缺fi、明显签名错误可先静态排查。但工具链升级与historical verifier接受性确实需要正确版本的证据，纯静态不宜声称“无问题”。skill的“CI verification is a review precondition”与这些故意不可验证的bench输入不相容，应把“CI未确认”明确记录为未覆盖。

### 4.5 根因、差分范围和证据元数据需要更严格

已核对的具体错误：#530把 `Self::NR_LEVELS_spec() == NR_LEVELS` 描述为新增；实际before第146行已存在，after第147行保留。标签针对新增的BASE_PAGE_SIZE与entry ratio限制。故仅记部分命中，而非完整命中，并把“新增性”陈述列为已证实的范围判断错误。

#136报告头的head写成 `3319ef…`，而基准及目录实际head是 `948309…`；#146 `b4c6…` 报告头的head写成 `674715…`。正文仍分析问题快照的代码，但头部来源可能混用了历史证据。不要从这两例推断所有报告都有该问题；建议由runner写入不可变sample_id、真实SHA与diff哈希，模型不得自行推断。

### 4.6 不能把不完整运行等同于 skill 设计缺失

当前skill要求各persona分工、逐规则覆盖、反驳检查，并允许有明确问题的隔离caller实验。报告反复说明fast override跳过了穷尽清单、history和实验；部分报告也明确跳过sub-agent pass。若这些确为用户有意的运行约束，则不属于违规执行；但评测结果只能描述这个轻量配置。

Specification persona本来已写明identity、ownership effects、最终可变参数状态、Ok/Err和caller-next-obligation。因此资源问题漏检不宜简单解释为“skill没写这些要求”；更可能是执行深度不足、清单没有可审计产物、静态候选过早筛选等。没有本次runner原始prompt/完整trace，无法进一步确定因果。

## 5. 基准任务本身的混杂因素

**快照缺陷检测与diff回归review不同。** #403标签描述take/put复制权限，after已经换成borrow；#499标签全部定位before的替代PTE实现，PR删除替代模型并验证实际实现。把它们视为after仍需报告的bug会奖励错误指控。

此外，#35的4个未命中标签被报告明确视为既有admit而排除；#39标签所在证明文件不属于diff变更路径。这些说明仅排除2个X还没有完全消除范围不一致。本文的36.5%敏感性数字不是“已经公平校正”的最终skill得分；完整scope adjudication需要重新定义每标签是否必须在该review任务内检出。

**workflow边界也不一致。** skill把workflow限定为rlimit和upstream reusable specs；bench却包含shell语法、bootstrap失败处理等。当前运行偶尔跨出了这个范围并抓到#220的`|| true`，但漏掉其他CI问题时，需区分能力不足与预设任务范围。

**当前完成样本不是随机测试集。** 样本多为较早编号，且运行顺序看起来与目录字典序相符；不要把35.9%外推为全部179样本或未来PR的稳定召回率。同PR多个快照也有相关性，所以没有给出假装各标签独立同分布的置信区间。

## 6. 建议的改进顺序（仅建议，未修改）

1. **先对齐评测协议。** 显式选择 `introduced_or_modified` 或 `snapshot_all_existing`；after已修复标签另设“修复识别”，不混入新缺陷召回。区分CI前置已满足/未知/已失败。先固定sample_id、哈希、review模式和规则版本。
2. **保留廉价覆盖检查，即使fast模式。** 每条当前规则输出F/通过/不适用/未检查及位置；内部表应随运行保留，避免只存最终finding而无法区分“检查了没发现”和“没查”。命名、模式、导入、比较、cast等不应依赖是否碰巧注意到。
3. **加入明确的基本正确性检查。** 缺字段、模块、trait项、条件编译导入、shell闭合、workspace依赖、exec/spec mode先检查；工具链敏感问题在未知时报告coverage gap。需要实验时在隔离环境使用正确版本，不必全面重复CI。
4. **把资源与模型检查变成具体问题。** 对每个可信constructor询问“能否重复调用获得第二份权限”；对每个ghost output询问“如何绑定receiver”；对Err/None和drop/wake询问“哪些资源被归还”；对量词检查domain覆盖、空集/域外witness、矛盾antecedent；对roundtrip检查两个方向而非只看名字。
5. **优先检查真实边界而非当前caller都能通过。** 测试rc=MAX-1、level=0/最大值、非CPU paging配置；模拟跨页表边界、锁状态转换、失败后第二次调用。#454、#546、#612适合作为回归样本。
6. **复核新增性与候选质量。** 每条finding保存对应diff hunk；先确认是否引入/实质改变，再定severity。将“合法但尚未验证的候选”与“可发布阻塞项”区分。skill当前要求uncertain保留且加unverified，这有候选堆积风险，但本次没有足够证据证明它造成多少误报。
7. **下一轮做同输入的受控对比。** 固定这96份输入，比较当前fast、fast+结构清单、完整persona流程；记录耗时、token、严格/宽松召回、独立裁决后的precision。用另一个未调参样本集验证，避免只针对这117个标签优化。
