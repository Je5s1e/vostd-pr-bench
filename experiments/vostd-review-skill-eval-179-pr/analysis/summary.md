# VOSTD Review Skill 评估：省流版

## 评估了什么

本次评估的是 VOSTD 项目中 **164 个历史 PR 的 179 个代码快照**，涉及 Rust/Verus 的内存与页表、并发与资源管理、底层接口及构建工具等变更。同一个 PR 可能有多个快照，完整名单见[快照索引](sample-index.md)。

按报告记录，全部快照均使用 `vostd-code-review` skill 完成 **fast 静态审查**，再对照基准中的 **244 个已知问题**进行根因匹配。下文统一汇总全部179个快照。这一配置没有执行完整审查流程或历史 Verus 验证；结果反映该轻量配置的表现。

## Review 结果

以下“完整发现”要求指出**同一个具体问题的根因**，仅提到同一文件或相近风险不算。发现比例越高，表示已知问题覆盖越好。

### 1. 总体发现了多少问题

| 已知问题类型 | 完整发现 / 已知问题 | 发现比例 |
|---|---|---|
| **全部问题** | **58 / 244** | **23.8%** |
| 语义与正确性问题 | 47 / 133 | 35.3% |
| 编码与证明规范问题 | 11 / 111 | 9.9% |

其余标签中，**7个部分发现、176个未匹配、3个已被对应PR修复**。把部分发现计入后为 **65/244 = 26.6%**；排除3个已修复标签后，完整发现比例为 **58/241 = 24.1%**。

### 2. 有多少份报告覆盖了已知问题

| 每份快照的表现 | 快照数 | 占179份的比例 |
|---|---|---|
| 已知问题全部完整发现 | 41 | 22.9% |
| 至少一个完整发现，但未覆盖全部 | 7 | 3.9% |
| 没有完整发现任何已知问题 | 131 | 73.2% |

合计 **48/179 = 26.8%** 的快照至少有一个完整命中。另有 **155份报告提出了意见，24份没有意见**：提出意见不等于命中已知问题，“没有完整命中”也不等于所有意见无效。

### 3. 报告提出的意见是什么情况

| 报告自评严重度 | 意见总数 | 完整关联已知问题 | 仅部分关联 | 未关联 |
|---|---|---|---|---|
| 高 | 124 | 35 | 5 | 84 |
| 中 | 135 | 17 | 2 | 116 |
| 低 | 41 | 4 | 0 | 37 |
| **合计** | **300** | **56** | **7** | **237** |

**未关联不等于误报。** 未关联意见可能是基准未收录的新问题，目前尚未完整复核；因此不能用上述比例计算真实准确率或误报率。高、中严重度合计 **259/300 = 86.3%**；其中高严重度仍有 **84条未关联**，值得优先复核。严重度是原报告自评，不是独立确认的风险等级。

一条意见可能包含多个问题，多个意见也可能共同说明一个问题，所以“56条完整关联意见”和“58个完整发现的问题”不矛盾。

## 哪些方面较好，哪些方面较差

### 4. 按具体问题类型看强弱项

| 具体问题类型 | 完整发现 / 已知问题 | 发现比例 |
|---|---|---|
| 显式证明缺口（admit / external_body） | 15 / 27 | 55.6% |
| 运行行为与生命周期 | 7 / 18 | 38.9% |
| API契约、泛型与边界 | 10 / 28 | 35.7% |
| 状态机、不变量与模型 | 4 / 14 | 28.6% |
| 构建、工具链与证明能否通过 | 8 / 30 | 26.7% |
| 所有权、资源守恒与对象身份 | 3 / 17 | 17.6% |
| 执行代码保存与放置 | 3 / 18 | 16.7% |
| 命名、模式、导入与局部风格 | 5 / 49 | 10.2% |
| 规范复用、放置与闲置helper | 3 / 41 | 7.3% |
| 验证文档 | 0 / 2 | 0.0% |

- **相对强项是显式证明缺口，其次是运行行为和API契约。** 能抓到部分明显的证明缺失、执行路径变化和调用者无法使用的契约；但这三组仍分别只发现55.6%、38.9%、35.7%，远未全面覆盖。
- **最弱的是规范复用与helper检查、命名/模式/导入细节。** 这两组仅 **3/41、5/49**，说明轻量检查仍有很大补齐空间。
- **跨对象、跨调用的资源关系仍是重要短板。** 所有权组仅 **3/17**，容易漏掉权限未归还、账本与资源不同步、owner未绑定实际对象等问题。

此表使用与总体一致的原始分母；所有权组含1个已修复标签，模型组含2个。各组样本量不同，尤其文档仅2例，不能据此判定稳定能力。

### 5. 哪些具体规则最值得优先补齐

| 代表性规则 | 完整发现 / 对应标签 | 发现比例 |
|---|---|---|
| 未使用的辅助函数 | 0 / 10 | 0.0% |
| 复用已有规格 | 0 / 8 | 0.0% |
| 证明相关导入 | 0 / 6 | 0.0% |
| 辅助证明函数的放置 | 0 / 5 | 0.0% |
| 单调用辅助函数的局部化 | 0 / 4 | 0.0% |
| 量词与触发器写法 | 0 / 4 | 0.0% |
| 重复ghost/tracked模式标记 | 0 / 4 | 0.0% |
| 证明角色命名 | 2 / 9 | 22.2% |
| 按crate分组导入 | 1 / 6 | 16.7% |
| 保留原执行代码与来源记录 | 5 / 21 | 23.8% |

规则表与上一张“问题类型”表是两种分类视角。一个标签可以关联多个规则，**不能将此表直接加总，也不能将这些分数视为规则执行率**。例如保留执行代码规则包含部分语义问题，因此其5/21与问题类型表的3/18口径不同。

## 改进方向

1. **fast模式也必须保留逐规则检查清单。** 优先补命名、模式、导入、未使用helper和规格复用；后两项目前分别为 **0/10、0/8**，应先解决覆盖问题。
2. **将所有权检查写成明确的操作步骤。** 逐项跟踪资源从哪里来、被谁消费、失败时是否归还、返回后能否再次使用，并核对owner与实际对象身份；当前仅 **3/17** 完整命中。
3. **同时检查API的输入、成功、失败和最终状态。** 不只检查前置条件，还要检查 `Ok/Err/None`、返回值关系和跨模块可用性，减少“只检查了半份契约”的情况。
4. **增加一轮低成本的结构与差分检查。** 核对符号改名、声明与调用参数、模块和宏边界、锁文件及CI依赖；同时检查原代码、注释和可见性是否被不必要地改变。
5. **优先复核未匹配意见中的高严重度结论。** 237条未匹配意见中，高严重度有84条，应优先区分新问题、无效意见与证据不足项；不能只靠增加报告数量来提高检出。
6. **在统一范围和隔离输入后做成对对比。** 明确审查“本次变更”还是“整个快照”，清除历史evidence，固定预算，比较当前fast与新增检查步骤。用新的未暴露PR验证改进，避免只针对这批标签优化。

> 结论边界：匹配未经独立人工校准；当前16个样本目录残留历史evidence，是否在review时读取未知。因此，这批结果适合作为改进基线，不能直接当作严格隔离测试或skill泛化能力的证明。
